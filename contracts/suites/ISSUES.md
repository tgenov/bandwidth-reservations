# Contract suite issues

The contract suites test only what the frozen contracts state. When a contract does not state a
behaviour clearly, the suites do not test it, and the point is recorded here. Each item needs a
decision by the contract owner (an erratum or a new contract version). Until then, a provider and
a double can differ on the point, and both pass.

| Id | Contract | Point that is not clear | Real provider today | Double today |
|---|---|---|---|---|
| CS-1 | C01 §3.2, §2.4 | When `displacementRead` meets its lock timeout, the condition fails "as `'lockTimeout'`" in `conditionResults`. The contract does not say what `ConditionFailed.which` is: the condition label, or the literal `'lockTimeout'`. The account owner must tell a lock timeout (move the E5 to the next batch) from a displacement (no E5) | `which: 'lockTimeout'` | Cannot give a lock timeout |
| CS-2 | C01 §3.1, §2.4 | "Rebuilding a partition" reads the partition's log rows, but `OwnerRuntime` (§2.4) has no operation for it. The link owner uses `readLog(partition, fromSeq)`, which only `CockroachOwnerRuntime` and the runtime double have. The contract does not say if `readLog` is part of the runtime interface | `readLog` on `CockroachOwnerRuntime` | `readLog` on `RuntimeDouble` (added for the C01 suite) |
| CS-3 | C02 "Link hold port", `convert` | `convert` for a request whose hold was refused, or was released, can answer `NO_HOLD` or `TOMBSTONED`. The contract lists both as violations, but does not say which one applies to which state | `TOMBSTONED` | `NO_HOLD` |
| CS-4 | C02 "Idempotency", `release` | "The latest `D` sets the end of the tombstone." It is not clear if "latest" means the largest `D` or the `D` of the most recent `release` | The largest `D` | The `D` of the most recent `release` |
| CS-5 | C02 "Conventions", `LinkStamp` | `linkSeq` is the link's log position. The contract does not say which position a reply to a duplicate carries: the position of the entry that recorded the state, or the present position | The recorded entry's position | A new, higher value |
| CS-6 | C06 §7, §8 | `ledgerLastSeq` on `prior_total_mismatch` when the ledger has posted nothing for the line key. The rating rule "next amendment sequence = `ledgerLastSeq` + 1" suggests −1, but the contract does not state it | Real ledger (MONEY-I2): the fields are absent when the ledger has no posting of the line key | −1 |
| CS-7 | C06 §8, §9; RFC-004 §B1.2 | "The ledger refuses it, records the refusal": the contract does not say if a recorded movement-level refusal takes a sequence of the partition log. `LedgerPosition.sequence` is "the partition log sequence". `runC06ProviderSuite` expects contiguous movement sequences after a refused usage batch | Real ledger (MONEY-I2): a refusal is a log entry (audit), so movement sequences can have gaps; it is not the recorded answer of the `movementRef` (V63-2 records only `refused_batch` and `over_limit`). MONEY-I3: a refused usage batch (`refused_batch`) is the recorded answer and writes no log entry, so it takes no sequence and the suite's contiguous sequences hold; a movement-level refusal (`invalid`, `principal`, `wrong_home`) is still a log entry | Contiguous |
| CS-8 | C06 §9 | Each view copy has "the same `EventId`" as the full feed. On the C01 runtime each stream has its own `stream_seq`, and a stream is keyed by a declared event field. The contract names no key field for the supplier and external views | Real ledger (MONEY-I2): the body `eventId` is the full feed's; Kafka headers carry the view's own stream sequence; each copy has the added field `view_key` | No double |
| CS-9 | C06 §2, §8; `runC06ProviderSuite` | The usage suite builds M5 entries that credit the whole charge to the one supplier of its route (`B −a`, `S:<supplier>:earn +a`). C06 §2 needs a positive commission weight, so the Webster split of RFC-004 §B3.2 always gives the commission a share of a large enough charge. The suite does not state the weights for which its entries are the template. Since S-RATE-I4 (review 73 TR-4) `runC06ReservationSuite` tests the M5 and M6 templates on the multi-party weights 3000/3333/2167/1500 | Real ledger (MONEY-I3): the subject route has supplier weight 10⁹ and commission weight 1, so every suite amount (below 5 × 10⁸ µ) gives the commission 0 and the suite entries are the template. The ledger checks each line against the template (C06 §8 check 2) | Settlement double of the rate slice: the subject route has supplier weight 1 and commission weight 0; the ledger double checks each M4, M5 and M6 line against its Webster template |
| CS-10 | C06 §5 "Lines" (m5), §8; RFC-003 §5.6, §5.7; P3-S32 row 2 | A usage line closed at 0 micro-USD is not emitted (amounts are non-zero). When late traffic raises it to 1, P3-S32 row 2 and RFC-003 §5.7 want "an amendment of 1 with the reason late traffic" with "the original still 0". C06 permits no such output: a `seq 0` line has reason `original` (m5), and an amendment whose predecessor is not posted is `out_of_sequence`. The C06 contract owner must decide (an RFC-003 §5.6/§5.7 erratum that the first non-zero total is the late original, or a C06 change). Also C06 §5 does not list a late record as a `triggerRef` | Not reached (rating is the producer) | Rating (S-RATE-I4) emits the late original (`seq 0`, `original`, `reasonDetails.trigger = late_traffic`, the first record identity in `triggerRef`), posted as M5. Test `should post a late original at seq 0 when a line closed at 0 gets late traffic (P3-S32 row 2 conflicts with C06 m5)` |
| CS-11 | C06 §8 check 2 (D4); `runC06ReservationSuite` | "`weightsVersion` must be the version that the original of the line was posted with". The reservation subject knows one weights version, so the suite sends the amendment with a version the subject does not know (`w-other`). A provider that checks only the template of the line's own version also refuses it. A second known version needs a subject operation that the contract does not have | Real ledger: checks the version of the original before the weights lookup | Settlement double: checks the version of the original; a rate-slice test with two known versions proves it (`slices/rate/rating-owner/test/contract.c06.test.ts`) |
| CS-12 | C02 "Link waiting port", `mark_waiting` | The reply to `mark_waiting` for a request that has no hold and no waiter at the link (not seen, or its state is final) is not stated. `MarkWaitingReply` has only `APPLIED` and `IGNORED_OLDER` (S-LINK I5 DI-22) | `IGNORED_OLDER`, no entry; for a request that it has not seen, also the alert `MARK_WITHOUT_REQUEST` | No I5 part |
| CS-13 | C02 `ClaimSeq`, `YIELD_REQUEST` identity | A claim is "the link-log sequence of the entry that raised it". One entry (a scan, or a mark that checks several older waiters) can raise claims for more than one waiter. Two requests on one holder attempt from one entry would have the same identity (link, request, attempt, kind, claim) (S-LINK I5 DI-21) | One entry raises at most one request on a holder attempt: for the first waiter that the entry checks (the oldest in a scan or a mark) | No I5 part |

These are behaviours that the contract states and the real provider has, but that a double does not have
yet. The suite registers a PENDING entry for the double, so the gap shows in every run.

| Contract | Behaviour | Double | Provider has it since |
|---|---|---|---|
| C02 `hold` checks (5), (7); `query`; link availability query | The counter-offer on `NO_FIT` and `IN_FLIGHT`, `query`, `availability` and `fit_ranges` (`runC02ProviderSuite(…, { i2: true })`) | Account link double (`slices/account/owner/testing`) | S-LINK I2 |
| C02 `hold` check (8); link waiting port | `WAITING(1, aheadDeadline)`, a grant that keeps the attempt, and the `GRANTED` notification with the same identity on the push and the relay (`runC02ProviderSuite(…, { i2: true, i3: true })`: provider tests 1, 4 and 13). The double has no I2 part, so the I2 PENDING entry stops its suite before the I3 part. The double throws on `wait = true` | Account link double (`slices/account/owner/testing`) | S-LINK I3 |
| C02 `hold` check (4) | `INVALID(rule)` for V1 … V6 against the receipt minute `m0`, with the calendar cases of P1-S74 (`runC02ProviderSuite(…, { i4: true })`) | Account link double (`slices/account/owner/testing`) | S-LINK I4 |
| C02 `YIELD_REQUEST`, `mark_waiting`, `yield_accept`, `yield_refuse` | Provider test 4 (yield parts: `ACCEPTED(attempt + 1)`, `STALE_ATTEMPT`, the end of an attempt closes its claims) and provider test 5 (both orders of refusal and mark; a refusal ends only its claim) (`runC02ProviderSuite(…, { i2: true, i3: true, i5: true })`).

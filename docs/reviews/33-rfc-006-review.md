## Verdict

**ACCEPT WITH CHANGES.** The review finds 0 Blockers, 4 Majors and 14 Minors (18 findings).
A fix verification should confirm R33-01 … R33-04 before an owner RFC is approved against
§12.

Review 27's three Blockers are resolved, and the fixes are sound:

- **R27-01 (resume).** I re-ran the trace: X decided at `t_x`, a lapse, a rule-3 read at
  `r`, then a renewal. The rule-3 read of the session row leaves a timestamp-cache entry at
  `r`, so the renewal commits above `r`. The resume read's `T_res` is above the renewal, and
  `P := T_res` puts every later `P_grant` above `t_x`. The view arithmetic (only `max_offset`
  enters, measured from the send) is correct. **One sibling path is left open**: re-home
  (R33-01).
- **R27-02 (moves).** The report fence (`adopt` conditional on `head(A, '').report_through ≥
  ts(moved)`), rule 4 for moved partitions, `adoptTs` in `leasedRead`, and the per-partition
  `read_lease` + ε wait close the trace. The new protocol has a routing gap during lazy
  doubling (R33-04), and its fence read contends with the old slot (R33-07).
- **R27-03 (closure).** Flush, then progress, then offset, with the emitter's minimum over
  every `cdc` partition, is sound. Even a stale or zombie relay instance can only publish
  progress for rows Kafka has already acknowledged. `CLOSED`'s `feed_seq` read `AS OF
  SYSTEM TIME t` is exact. The remaining defects are contract precision and operability
  (R33-08, R33-14).

The four Majors are all local:

1. Re-home has no report-position floor (R33-01).
2. The anycast withdrawal rule needs a view of the other region that the partitions it
   names make impossible (R33-02).
3. A metro split leaves half of all Kafka partition leaders unreachable (R33-03).
4. Lazy doubling mis-routes moved accounts until their slot is marked split (R33-04).

## Decisions taken

None of these blocks the RFC. Each weighs buyers (including AI agents), suppliers, Share's
risk and operability.

| # | Question | Decision | Why |
|---|---|---|---|
| D1 | Who arbitrates "the other region is passing" for anycast withdrawal? | **The probe sites**, outside Share's facilities, over the public internet. With no arbiter reachable, never withdraw (R33-02) | Both partitions D3 was meant for (a double cut, an isolated R1) leave the regions blind to each other. The probe sites already see both regions' unicast addresses. Failing closed keeps D3's "never black-hole" property |
| D2 | Kafka on a metro split: automatic leader consolidation, or operator action? | **Automatic**, through the controller, with the database consolidation (R33-03) | Feeds carry 10 s targets (X2-S17, X2-S22) and the webhook promise. Moving leaders loses nothing, because facts are in the database |
| D3 | Routing during a lazy split: a "splitting" state, or per-account overrides? | **A "splitting" state with the head row authoritative for the moving half** (R33-04) | One version per slot instead of one per account, and it also closes the account-creation race. Overrides would add about 49,000 map versions per doubling |
| D4 | `min.insync.replicas` on a correlated in-sync shrink without a topology state | **Lower to 2 automatically** on the observed shrink (R33-10) | Same reasoning as review 27's D2: Kafka is transport, and keeping feeds flowing outweighs the single-region window of a few seconds |

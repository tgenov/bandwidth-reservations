## Verdict

**INADEQUATE.** 1 Blocker, 5 Major, 6 Minor.

The scenario tests use exact micro-USD values and exact sequences. The order property test is seeded, prints the seed, and uses an oracle (exact `bigint` rationals, its own spread and floor) that shares no code with rating. The stalled-watermark fix has a test that fails without the fix. The settlement double really runs `runC06ReservationSuite`. That part is strong.

But one money guard survives a mutant: the guard that stops an amendment of 0 micro-USD (TR-1). A late record that does not move the floor of its line is the most frequent kind of late record. Without the guard, rating emits a zero line, settlement refuses the usage batch, and the line and every other line of that batch stay unposted. No test sends such a record. Also the P3-S32 row 2 test proves the scenario only on an internal entry. The charge-line feed and the ledger show the opposite of the scenario text (TR-5, a design finding).

## Focus questions of the brief

**(a) Money: integer micro-USD, order independence, no double posting, rounding.** All amounts are `bigint` and integer strings. The amendment restates the total: `C − E` with `C = ⌊V/10^6⌋` (`chargeOf`, `usageCharge`). The scenario tests assert `amount`, `newTotal`, `priorTotal` and `seq` with exact equality, and P3-S32 row 1 asserts the M5 and M6 ledger entries. A sequence `k + 1` waits for `k` to be posted (test `should emit amendment k + 1 …`, which also asserts one line for each batch). Gaps: TR-1 (zero amendment), TR-2 (`usageReduction`), TR-3 (eviction of an unposted line from `U`).

**(b) Property tests against an independent oracle.** `order.property.test.ts` is good. The oracle uses its own GCD, its own spread over half-open minutes, the price of each minute (both sides of the 12:20 change) and one floor. It compares the ledger posted total of the last sequence of each line, in both runs, with the oracle. Seeds 1, 2, 3, 20261013 are fixed; `RATE_ORDER_SEED` runs one seed; each message names the seed. Both runs assert `unposted = 0` and no alerts. The gap: bytes are `1 + U[0, 2^32)`, so lines closed at 0, and late records that do not change the floor, almost never occur (TR-10). These are the cases of TR-1 and TR-5.

**(c) The stalled-watermark close fix.** A test fails without it (M3). The test asserts the exact timer (`base + 45 s`) and a closing time in `[base + 45 s, base + 46 s)`. A mutant `nowMs >= base + bound` → `>` in `closable` moves the close to `base + 46 s`, so the same test kills it (by reading).

**(d) The settlement double and `runC06ReservationSuite`.** The suite really runs: 8 `[settlement double]` reservation tests pass, and `contract.c06.test.ts` wires the double with the M4 template check (`weightsOf`). For reservation batches the double follows C06 (Webster M4, per-line exclusion, `batch_over_limit`, recorded answers). For usage lines it does not: M5 and M6 use a floor split with the remainder to the commission, not the Webster split of RFC-004 §B3.2, and the ledger double does not do the CT-L6 template and "weights of the original" checks for usage lines. The C06 usage suite has no test for these clauses, so the double passes it (TR-4).

**(e) P3-S32 row 2 workaround.** The test hides a behaviour that contradicts P3-S32 and RFC-003. See TR-5.
